# 02 · 架构原理

把 SimpleACR 每一层拆开讲清楚：它在干什么、为什么这么干、以及
AE / RSR / WrathCombo 这类成熟插件在同样的位置是怎么做的。

---

## 0. 全局数据流

```
IFramework.Update（游戏主线程，每帧）
      │
      ├─ 节流：距上次求值 < TickIntervalMs(100) 就 return
      │
      ├─ CombatState.Snapshot()          ← 抓一帧快照（读 Dalamud 服务 + ClientStructs）
      │      · 玩家 HP/MP/职业/等级
      │      · 目标 / 距离 / 目标血量
      │      · InCombat / InDuty / Mounted / Casting
      │      · GCD 总时长 / 剩余
      │      · 连招状态
      │      · 职业量谱
      │
      ├─ RotationManager.GetFor(jobId)   ← 拿到当前职业的循环表
      │
      ├─ 自动选敌（可选）：没目标 → 选最近的
      │
      ├─ 求值：for (entry in rotation.Entries)   ← 自上而下，命中即止
      │      if (!entry.Enabled) continue
      │      if (entry.Condition(st) == false) continue
      │      pick = entry; break
      │
      ├─ 节奏闸门 TimingAllowed(pick, st)
      │      GCD   → !st.GcdRolling && !st.IsCasting
      │      oGCD  → st.CanWeave()   // GcdRemaining <= OgcdWindowSec
      │
      ├─ 目标解析 ResolveTarget(pick.Target, st)
      │      Target / Self / LowestHpParty / NearestEnemy / Focus
      │
      ├─ 防抖：同技能两次施放间隔 < ActionDebounceMs 就跳过
      │
      ├─ 可用性：ActionExecutor.CanUse(id, targetId)
      │      → 原生 GetActionStatus == 0 ?
      │      （游戏帮你判 CD / 射程 / MP / 等级 / 咏唱 / 目标合法性）
      │
      └─ ActionExecutor.Use(id, targetId)
             → 原生 UseAction
```

---

## 1. 为什么必须跑在 `IFramework.Update`

`IFramework.Update` 是 Dalamud 暴露的**游戏主线程**帧事件。
FF14 的原生函数（尤其是 `ActionManager.UseAction`）不是线程安全的，
从别的线程调会：

- 读到半更新的内存结构
- 和游戏自己的逻辑竞争
- 极端情况直接崩客户端

所以引擎里**没有任何后台线程、没有 Task、没有 Timer**。
轮询间隔靠 `Environment.TickCount64` 手动节流，而不是 `Task.Delay`。

这是自动循环插件和"普通工具插件"最大的架构差别之一。

## 2. ActionExecutor —— 唯一的执行出口

```csharp
am->GetActionStatus(ActionType.Action, actionId, targetId) == 0  // 能按吗
am->UseAction(ActionType.Action, actionId, targetId)             // 按下去
```

### 为什么不让引擎到处调原生函数

把所有原生调用收在一个类里，好处是：

1. **版本适配只改一处**。大版本更新时 `ActionManager` 的签名常变，
   散落全工程的话每处都要改。
2. **可以加缓存**。Lumina 查表很慢，`GetRow` 加了 `Dictionary` 缓存，
   一帧内查同一个技能 ID 几十次也只查一次表。
3. **可以加保护**。空指针、异常都在这里兜住。

### GetActionStatus 的返回值

`0` = 现在能按。非 0 是具体失败原因（冷却中 / 射程外 / MP 不足 /
等级不够 / 正在咏唱 / 目标非法 ...）。

**不要试图自己判断"能不能按"** —— 游戏自己判断得比谁都准。
你的循环只管"想不想按"，可用性交给 `GetActionStatus`。

这是新手最常犯的错：在条件里手写 `s.Cd(x) <= 0 && s.Mp > 1000 && ...`，
结果漏了某个边界情况，然后奇怪为什么技能按不出来。

### 冷却查询

```csharp
row.CooldownGroup            // Lumina Action 表，1-based
am->GetRecastGroupDetail(group - 1)   // 0-based，注意 -1
detail->IsActive != 0        // 是否在转
detail->Total - detail->Elapsed       // 剩余秒数
```

`CooldownGroup` 为 0 或 1 = 没有独立冷却（跟着 GCD 走）。

### GCD

GCD 就是一个特殊的复唱组：

```csharp
public const int GcdRecastGroup = 57;
am->GetRecastGroupDetail(GcdRecastGroup)->Total;   // 总时长（受技速影响，实时变）
am->GetRecastGroupDetail(GcdRecastGroup)->Elapsed; // 已过
```

> ⚠️ 这个 `57` 是社区常用常量，但**它不是保证不变的**。
> 如果你发现 UI 上 GCD 一直是 0 或乱跳，用 `/sacr dump` 对比实际转圈时间，
> 改掉这个常量即可。这是唯一一个"版本相关、需要人肉校准"的值。

### 充能层数

`CurrentCharges()` 是基于 Lumina 表的**估算**：

```
层数 = 最大层数 - ceil(剩余冷却 / 单层恢复时间)
```

够用了（调停 2 层、猛攻 3 层这类判断不会错）。
如果你的 ClientStructs 有原生 `GetCurrentCharges`，优先换成原生的 —— 代码里有注释。

## 3. CombatState —— 快照 + 条件库

### 为什么要快照

两个原因：

1. **一致性**。同一帧内所有条件看到的必须是同一份数据。
   如果每个条件各自去读一次 `LocalPlayer`，理论上可能读到中途变化的量。
2. **性能**。`GetActionStatus` / `GetRecastGroupDetail` 都是跨 native 边界的调用，
   一帧内调用几十次是有开销的。快照一次，后面全读缓存。

### 移动检测

Dalamud 没有现成的 `IsMoving`。做法是**两帧位置差 / 时间差**：

```csharp
float dt = (now - _lastSnapshotMs) / 1000f;
float moved = Vector3.Distance(pos, _lastPosition) / dt;
IsMoving = moved > 0.5f;
```

比读 `Character` 结构体里的移动字段稳（那个字段的偏移量每次更新都可能变）。

### 职业量谱为什么要 try/catch

量谱结构体是逆向出来的，字段名跟着版本走。
7.0 之后好几个职业的量谱字段改过名。

一个量谱读不到，最坏的结果应该是"这条条件不成立"，
而不是整个引擎崩掉。所以统一包一层：

```csharp
private static int ReadGauge(JobGaugeKind kind)
{
    try { return kind switch { ... }; }
    catch { return 0; }
}
```

## 4. RotationEngine —— 心脏

### 4.1 求值：命中即止

```csharp
foreach (var entry in Current.Entries)
{
    if (!entry.Enabled) continue;
    if (entry.Condition != null && !entry.Condition(st)) continue;
    pick = entry; break;
}
```

O(n)，n 是一份循环里的条目数（一般 10~20 条）。
每 100ms 跑一次，开销可以忽略。

**这个模型的全部表达力都在"顺序"上。**
同一组技能，换个顺序就是完全不同的循环 —— 这就是 AE 那个"ACR 脚本"的本质。

### 4.2 节奏闸门

```csharp
ActionCategory.Gcd       → !st.GcdRolling && !st.IsCasting
ActionCategory.Ogcd      → st.CanWeave()  // GcdRemaining <= OgcdWindowSec
ActionCategory.Defensive → st.CanWeave()  // 受独立开关控制
```

**GCD 技能**：GCD 在转 → 按不出来，等。咏唱中 → 也按不出来。

**能力技**：关键在窗口。时间线是这样：

```
|--使用 GCD 技能--|--- GCD 开始转（2.5s）---|GCD 转好|
                  ^                        ^
                  |                        |
         这段时间按 oGCD              oGCD 要在这里按
         会把 GCD 往后顶
```

所以 `CanWeave()` 是 `GcdRemaining <= 0.6`。
延迟高的玩家要调小这个值（0.3~0.4），否则能力技会在服务器看来"按晚了"。

### 4.3 防抖

```csharp
if (_lastUsedAt.TryGetValue(actionId, out var last) && now - last < ActionDebounceMs)
    return;
```

问题场景：你按下技能 → 客户端开始动画锁 → **服务器还没回包确认** →
下一帧 `GetActionStatus` 可能仍返回 0（CD 还没生效）→ 又按一次。

防抖 200ms 足够覆盖这个窗口。

### 4.4 异常隔离

```csharp
try { Tick(now); }
catch (Exception ex) { Service.Log.Error(...); StatusText = "异常，详见 /xllog"; }
```

这是**必须**的。循环脚本是你自己写的，条件里一个 `NullReferenceException`
如果不接住，会一路冒到 Dalamud 的帧循环里，轻则报错刷屏，重则游戏崩。

包住之后：最坏这一帧不动，日志里有完整堆栈，游戏照常跑。

## 5. RotationManager —— 反射注册

```csharp
foreach (var type in Assembly.GetExecutingAssembly().GetTypes())
{
    if (type.IsAbstract || !type.IsSubclassOf(typeof(Rotation))) continue;
    var attr = type.GetCustomAttribute<RotationAttribute>();
    if (attr == null) continue;
    ...
}
```

启动时扫一遍，把所有带 `[Rotation]` 的类 new 出来、跑一次 `Build()`、
按职业 ID 存起来。

**好处**：加一个职业 = 加一个文件，引擎零改动。
这就是 AE「ACR 脚本热加载」的最简实现 —— AE 走的是服务端下发 + 运行时编译，
我们走的是编译期反射，原理一模一样。

### 启动校验

```csharp
foreach (var e in rotation.Entries)
    if (!ActionExecutor.Exists(e.ActionId))
        warns.Add($"「{e.Name}」引用的技能 ID {e.ActionId} 不存在");
```

**这一步救过很多次命。** 技能 ID 写错的症状是"这个技能永远不按"，
在几十条循环里肉眼找非常痛苦。启动时直接列出来，省时间。

## 6. 和 AE / RSR 的对比

| | SimpleACR | AEAssist | Rotation Solver Reborn |
|---|---|---|---|
| 循环表示 | C# DSL（优先级表） | ACR 脚本（服务端下发） | `IAction` + `UseIf` |
| 注册方式 | 编译期反射 | 运行时下载 + 编译 | 编译期 |
| 时间轴 | ❌ | ✅ 精确到毫秒的轴 | 部分 |
| 目标选择 | 5 种策略 | 丰富（含队友/团减） | 丰富 |
| 自动走位 | ❌ | 配合 vnavmesh | 部分 |
| 代码量 | ~1500 行 | 闭源 | ~3 万行 |

SimpleACR 学的是**架构思想**，不是功能对等。
把这份代码看懂之后，去看 RSR 的源码会轻松很多 —— 它的核心也是
"一张优先级表 + 一个调度器"，只是加了很多很多的工程细节。

## 7. 这个简化版**没做**什么

知道了边界，才知道往哪加：

| 缺失 | 说明 |
|---|---|
| **时间轴 / 机制处理** | AE 最强的地方。零式绝本的减伤轴、奶轴靠时间轴精确到毫秒 |
| **GCD 预输入** | 成熟插件会在 GCD 还剩 0.2~0.5s 时就开始尝试按，抵消网络延迟 |
| **咏唱中插能力技** | 读条职业要在咏唱最后 0.5s 插，本项目的闸门简单地禁止了 |
| **动画锁感知** | 需要 hook `UseAction` / `ReceiveActionEffect`，本项目没用 hook |
| **多目标加权选择** | 现在只是"最近的敌人"，没做仇恨/血量/位置加权 |
| **移动预测 / 走位** | 完全没做，需要 vnavmesh |
| **爆发窗口对齐** | 团辅对齐（如 2 分钟爆发）需要读队友 buff，本项目没读 |

这些每一个都能单独写一篇。先把骨架跑通，再一个一个加。
